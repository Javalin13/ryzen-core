## Capability versus mechanism versus authority versus skill profile

- **Authority:** which canonical Brain/layer owns a sovereign responsibility.
- **Capability:** what the ecosystem must be able to do.
- **Mechanism:** how architecture implements, assists, constrains or verifies that capability.
- **Skill profile:** a measurable quality/technique that an existing owner may need to perform its canonical responsibility reliably.

A skill profile does **not** gain sovereign authority merely because it has a dedicated document.

## Routing rule for cognition/model degradation

When a cognition path becomes less dependable, route by **cause and responsibility** rather than inventing a generic new authority:

- **model/provider/substrate capability degradation** → Layer 18;
- **alignment/coherence/constraint drift during cognition** → Layer 11;
- **hidden fragility/failure-mode discovery** → Layer 19;
- **self-model/emergent-cognition/anomalous scientific phenomenon** → Layer 22;
- **historical/state continuity problem** → Layer 21 and/or Layer 15;
- **constitutional propagation/outcome-chain degradation** → Layer 16;
- **operational ARC reliability trend** → OMEGA, feeding reusable prevention to FACTORY.

The same observed symptom may require several existing owners to cooperate. **Shared awareness is allowed; duplicated sovereign responsibility is not.**

## Model-substrate rule

The reliability capability library is model-agnostic. It may describe techniques relevant to LLMs, RLM patterns, model ensembles, hybrid/neurosymbolic cognition, future world-model systems, future Looped World Model implementations if Founder-approved more precisely, and embodied ARC cognition.

Canonical architecture already anticipates substrate evolution. No substrate name becomes a new canonical tier merely because it is technologically important.

## Addition test

Before creating another detailed capability file, ask:

1. Which existing canonical Brain/layer owns the underlying responsibility?
2. Is this merely a measurable skill/technique that owner needs?
3. Is a mechanism already defined?
4. Does a current profile already cover it under another name?
5. What concrete reliability failure remains insufficiently handled?
6. Would adding a new owner violate non-duplicated authority?
7. Can the improvement be implemented/tested inside the existing owner instead?

If an existing owner can absorb it, **REFINE/CROSS-LINK rather than create new architecture**.
