## Purpose

This matrix exists so RYZ3N does **not** create a second architecture merely because a reliability concern can be given a new name.

Before a future reliability capability is added, it must be checked against:

1. the canonical corpus in `Javalin13/ryzen-continuity` and the original conceptual-architecture documents;
2. Founder-approved constitutional evolution in `ryzen-core`;
3. approved runtime/productization standards;
4. PRIME / OMEGA / FACTORY current operating contracts;
5. implemented or scaffolded mechanisms;
6. the distinction between a **capability** and the **mechanism** that supplies it.

The rule is:

> **Reuse existing authority and mechanisms before creating a new capability label. Add only a missing cognitive or operational capability that materially improves Reliable Excellence.**

## Source-order rule

For material architecture interpretation, use the existing constitutional load order. In simplified form:

`canonical continuity / original conceptual corpus → Founder-approved evolution → implementation standards → runtime evidence`

Conversational memory or a convenient implementation pattern may not silently outrank those sources.

## Capability versus mechanism

- **Capability:** what the system must be able to do reliably.
- **Mechanism:** how the current architecture implements, assists, constrains or verifies that capability.
- **Authority:** which Canon / Founder-approved rule defines the boundary.

A capability may use several mechanisms. A mechanism may support several capabilities. Naming a mechanism again as a new layer is duplication.

## Model-substrate rule

The reliability capability library is **model-agnostic**.

It must remain applicable when cognition is supplied by:

- LLMs;
- RLM / recursive language-model patterns;
- multiple-model ensembles;
- hybrid or neurosymbolic substrates;
- future world-model systems;
- future Looped World Model implementations if/when Founder-approved architecture defines that substrate more precisely.

Canonical ARC architecture already anticipates substrate evolution, including world-model systems. During this 2026-09-14 review, no standalone authoritative document named **`Looped World Model`** was found in the checked canonical GitHub/Drive corpus. Therefore the phrase is preserved as a Founder-mentioned future substrate direction, **not silently promoted into a new canonical layer by this library**.

The reliability architecture must survive model replacement.

## Truth-boundary rule

The reviewed architecture already establishes the correct separation:

> **The model supplies intelligence. Durable control, evidence, Canon, mission state and verification determine what becomes system truth.**

Therefore this library must not create a second "truth engine". New cognitive capabilities feed the existing truth / verification / control architecture.

## Addition test

Before creating another detailed capability file, answer:

1. Is the capability already explicit in Canon?
2. Is it already owned by an existing Brain/layer/OMEGA/FACTORY/runtime standard?
3. Is the proposed item actually a mechanism rather than a capability?
4. Does a current capability file already cover it under another name?
5. What specific reliability failure remains insufficiently covered?
6. Can the capability be measured without creating architecture theater?
7. Does it remain model/substrate independent?

If questions 1–4 show sufficient coverage, **cross-reference rather than duplicate**.
