# RYZ3N Source, Bridge & Founder-Tracking Operating Mode

**Founder direction:** 2026-09-13  
**Status:** active operating standard  
**Constitution/Canon impact:** none — additive execution discipline only

## Purpose

Codify the working method already used across PRIME, ARCs and the Founder's private performance system so project truth, bridge state and personal execution evidence remain aligned continuously rather than being reconstructed from chat history later.

## Three-layer truth model

### 1. Project/source truth

The authoritative project repository remains the source of truth for architecture, runtime contracts, decisions, manifests, product work and ARC-local state that is appropriate for Git.

Examples:

- reusable RYZ3N standards → `Javalin13/ryzen-core`
- PRIME runtime/stewardship implementation → `Javalin13/prime-vps-migration`
- Cargo ARC/product truth → `Javalin13/CargoConnect`
- NARC truth → `Javalin13/NARC-ARC`
- VONDA truth → `Javalin13/VONDA-Corporation`

Never move authoritative domain truth into chat-only memory.

### 2. PRIME ↔ ARC bridge truth

Every active ARC keeps its respective bridge aligned with meaningful mission changes.

Bridge responsibilities:

- current routing mode and transition state;
- bounded handoff/continuation context;
- current blocker and next verified gate;
- source-freshness expectations;
- escalation state;
- reusable lessons that must cross the PRIME/ARC boundary;
- receipts for important transitions or runtime proofs;
- explicit protection against unrestricted private-memory mirroring.

PRIME maintains portfolio-level routing/stewardship context. Each ARC maintains its own direct bridge in its authoritative repository.

Bridge updates do **not** replace commits to the authoritative project files; they keep the parties synchronized around those commits.

### 3. Founder performance truth

The private `Javalin13/JohnDough` repository is the personal Founder performance/history layer.

Material work sessions should be captured there with evidence such as:

- work span and confirmed hours when known;
- deep-work / troubleshooting share;
- concrete outputs and commits;
- decisions closed;
- blockers removed;
- projects advanced;
- leverage created;
- highest-value result;
- biggest drag;
- next priorities;
- final performance score only when evidence and Founder-confirmed hours support it.

Hours are never invented. Project-private/customer-private payloads are not copied into the personal performance repo; only bounded performance evidence and generalized outcomes are recorded.

## Continuous alignment rule

For meaningful work, the operating loop is:

```text
work / decision / runtime proof
        ↓
update authoritative project source
        ↓
update relevant PRIME ↔ ARC bridge state
        ↓
record material Founder performance evidence privately
        ↓
continue from the aligned checkpoint
```

This is a continuous process, not an end-of-day cleanup ritual.

## What counts as a meaningful synchronization point

Synchronize when at least one of these occurs:

1. architecture or routing decision changes;
2. model/provider/runtime route changes;
3. ARC lifecycle or Owner-binding state changes;
4. significant blocker is isolated or removed;
5. controlled restart / live GREEN proof completes;
6. bridge mode changes;
7. Factory/OMEGA birth or lifecycle state changes;
8. commercial/product roadmap changes materially;
9. a reusable lesson or safety correction is discovered;
10. a material Founder work block produces concrete leverage.

Do not create noisy commits for every shell command. Capture meaningful state transitions and evidence.

## Source freshness before mutation

Before changing a project or ARC:

1. identify the authoritative repository/path;
2. inspect/reconcile current source freshness;
3. preserve local/remote valid work;
4. make the minimal intended change;
5. verify the result;
6. update bridge/continuation state when material.

No destructive history rewrite merely to simplify alignment.

## Bridge privacy rule

PRIME supervision receives bounded status, health, decisions, receipts and explicit escalation context. It does not require unrestricted ARC conversations, Owner private memory, secrets or customer payloads.

**Share state needed for stewardship; do not federate private payload by default.**
