# E1.25 ResourceExhausted Classifier Mapping — 2026-09-17

Status: **CLASSIFIER CONTRACT PROVEN; live-path classification still to verify**

## Source evidence

Hermes `agent/error_classifier.py` defines:

- `FailoverReason.rate_limit` for 429/quota-based throttling;
- `FailoverReason.overloaded` for 503/529/provider-overload conditions;
- explicit code mapping: `resource_exhausted`, `throttled`, and `rate_limit_exceeded` map to `FailoverReason.rate_limit`.

The classifier therefore has an intended contract in which a real `resource_exhausted` error code becomes `rate_limit`.

## Interaction with fallback health policy

`try_activate_fallback()` arms `_rate_limited_until` with exponential backoff starting at 60 seconds when reason is `rate_limit`, `billing`, or `upstream_rate_limit` before selecting the fallback entry.

Therefore, if the live Laguna `ResourceExhausted` error actually reaches `try_activate_fallback()` as `FailoverReason.rate_limit`, the next-turn primary restore should be gated for roughly 60 seconds.

## Remaining contradiction

Observed live behavior across successive Founder turns repeatedly re-probed Laguna before falling back to Qwen. This conflicts with the intended `resource_exhausted -> rate_limit -> 60s cooldown` contract.

The remaining possibilities are now narrow:

1. the live Laguna exception is not being classified through the `resource_exhausted` code path and reaches fallback with another reason;
2. the 60-second backoff is armed but later cleared/reset before the next turn;
3. the next Founder turn uses a fresh/different Agent instance/session so the process-local cooldown state is not retained.
