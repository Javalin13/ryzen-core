# E1.22A.4 — Runtime system-prompt persistence boundary

Date: 2026-09-15
Master: M3/16 — Cargo ARC GREEN
Execution line: E1.22 — provider-independent performance/context efficiency

## Observation

Read-only inspection of PRIME's Hermes `sessions` table showed recent sessions across Laguna, Super, Qwen and MiniMax with:

- `system_prompt_chars = NULL`
- `system_prompt_hash` populated

The table contains a `system_prompt` column, but current/recent sessions do not persist the prompt body there.

## Conclusion

The live PRIME system prompt measured by RYZ3N telemetry is assembled and used at runtime, while the database retains a prompt identity/hash rather than the full prompt text for these sessions.

Therefore E1.22 must operate at the Hermes system-prompt builder / request-assembly boundary, not by rewriting or retrieving session-stored prompt content.

## Architectural consequence

Do not treat `state.db` as the canonical body store for the live ~32.8k provider-facing system message. The relevant source of truth is the runtime composition path in `agent/system_prompt.py`, `agent/prompt_builder.py`, `agent/conversation_loop.py`, and Hermes prompt-cache modules.

The next acceptance step is to measure the actual `stable`, `context`, and `volatile` tier sizes produced by the live builder before any active compilation or reduction is introduced.

## Reliable Excellence constraint

No prompt reduction is allowed until tier boundaries and sizes are measured from the actual runtime builder. No historical session/tool content is to be modified as a substitute for runtime prompt engineering.
