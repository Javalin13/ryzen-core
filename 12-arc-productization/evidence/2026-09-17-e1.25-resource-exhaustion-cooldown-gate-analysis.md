# E1.25 ResourceExhaustion Cooldown Gate Analysis — 2026-09-17

Status: **ROOT-CAUSE NARROWING — no behavior change authorized yet**

## Context

E1.25 tests bounded degraded-path behavior after PRIME's primary Laguna route returned `ResourceExhausted` and Hermes served the turn through local Qwen fallback.

Observed same-turn behavior is bounded: the primary attempt is `attempt 1/1`, then fallback completes the turn. The remaining concern is cross-turn health handling: successive Founder turns re-probe the already exhausted primary instead of remaining on the healthy fallback for a bounded cooldown.

## Source evidence

`agent/chat_completion_helpers.py::try_activate_fallback` shows:

- rate-limit / billing / upstream-rate-limit reasons arm `_rate_limited_until` with exponential backoff starting at 60 seconds;
- the short `_FALLBACK_EXHAUSTED_COOLDOWN_S = 5.0` path is entered only when `_fallback_index >= len(_fallback_chain)` and the chain is exhausted;
- that branch returns `False` after arming the short cooldown.

The successful primary→Qwen fallback path instead proceeds into the next fallback entry, so the shown 5-second chain-exhausted cooldown is not evidence that a successful `ResourceExhausted` fallback arms cross-turn protection.

`agent/agent_runtime_helpers.py::restore_primary_runtime` correctly gates primary restoration when `_rate_limited_until > time.monotonic()`.

## Important correction

The earlier working hypothesis — "the existing 5-second cooldown is simply too short" — was premature.

The stronger current hypothesis is:

**successful fallback after `ResourceExhausted` may not arm `_rate_limited_until` at all, so the restore gate has nothing to enforce on the next turn.**

This distinction matters because the fix should target missing health-state arming, not merely inflate a cooldown constant.

## Next bounded proof

Inspect only assignments to `_rate_limited_until` and the successful fallback activation path after fallback selection. Determine whether `ResourceExhausted` on primary is mapped to a rate-limit-like health state anywhere after fallback activation.

Do not add a new RYZ3N circuit while Hermes already exposes a cross-turn restoration gate. Prefer the smallest adapter/runtime-policy correction if the existing mechanism can be reused.

## Acceptance target

After a primary `ResourceExhausted` event:

1. current turn falls back once and completes;
2. subsequent turns during cooldown use the healthy fallback directly;
3. primary is probed again only after cooldown/reset criteria permit;
4. recovery to primary is automatic when health returns;
5. no repeated full-context remarshal or retry storm occurs.

## Architectural implication

This remains runtime-adapter policy, not RYZ3N cognitive identity. RYZ3N should own the provider-health contract while Hermes is one replaceable implementation substrate.
