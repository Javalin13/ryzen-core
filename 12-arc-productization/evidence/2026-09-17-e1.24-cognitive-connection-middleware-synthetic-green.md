# E1.24 — Cognitive Connection middleware synthetic GREEN

Date: 2026-09-17
Master: M3/16 — Cargo ARC GREEN
Line: E1.24 verified context/capacity-pressure reduction
Status: SYNTHETIC CONTRACT GREEN; live provider proof still pending

## Purpose

Prove, without making a provider/model call, that the enabled `ryz3n-cognitive-connection` plugin can:

1. receive an R1 explicit no-tool turn through `pre_llm_call`;
2. retain the session/turn policy state;
3. expose registered `llm_request` middleware through Hermes' live plugin manager;
4. rewrite only the request-local provider payload;
5. remove tool-related request keys while leaving the canonical Hermes tool registry untouched.

## Prior root cause

The previous RED probe was not caused by the middleware implementation itself. Hermes `plugins list` proved that `ryz3n-cognitive-connection` v0.3.0 was installed and Plugin Doctor-valid but **not enabled**. Hermes user plugins are opt-in; only enabled plugins load.

The plugin was then explicitly enabled. Hermes required and received the privileged `allow_tool_override` grant because request/tool middleware can intercept or rewrite tool-routing behavior. PRIME gateway was restarted and returned `active`.

## Synthetic probe

The no-provider probe used:

- session id: `ryz3n-e124-probe`
- turn id: `turn-probe-2`
- `pre_llm_call` user message: `Without using any tools, answer briefly.`
- synthetic request containing `tools` and `tool_choice`
- `apply_llm_request_middleware(...)` through Hermes' real plugin machinery

Observed result:

```text
has_llm_request_middleware = True
changed = True
trace_count = 1
tools_before = True
tools_after = False
tool_choice_after = False
```

## Interpretation

GREEN for the runtime contract:

- the plugin is now genuinely loaded, not merely present on disk;
- Hermes sees the `llm_request` middleware;
- the Cognitive Connection R1 state reaches middleware correctly;
- request-local mutation occurs;
- `tools` and `tool_choice` are stripped for the bounded no-tool request;
- the change is scoped to the provider request rather than mutating global `agent.tools`.

This proves the intended architectural seam:

```text
RYZ3N turn classification
→ request-local cognition policy
→ Hermes llm_request middleware adapter
→ narrowed provider payload
```

## Security / privilege note

Hermes classifies this middleware path as privileged and required:

```text
plugins.entries.ryz3n-cognitive-connection.allow_tool_override: true
```

That grant is part of the Hermes runtime adapter contract and must be documented and revalidated on future runtime migration. It is not a general RYZ3N sovereignty grant; it is a substrate-specific permission required for request/tool interception.

## What this does NOT yet prove

Do not claim E1.24 fully GREEN yet. The following remain pending:

- live PRIME no-tool turn produces a non-zero middleware trace;
- live provider-facing request actually omits tool schemas;
- provider input/request size drops materially versus the prior ~20k-token / ~33k-char request baseline;
- no regression to ordinary R2+ tool-capable turns.

## Loading-bar effect

This closes the runtime registration/contract blocker and is sufficient for an executive Cognitive Connection progress update from **~55% to ~60%**.

The ~60% figure remains a directional implementation estimate, not a PRIME GREEN claim. E1.24 remains active until live provider evidence confirms the expected payload reduction.

## Portability implication

The durable RYZ3N contract is not `ctx.register_middleware("llm_request", ...)` itself. That is the Hermes adapter mapping.

The portable contract is:

> For R0/R1 turns, RYZ3N must be able to narrow the model-facing capability payload per request without destroying the runtime's canonical tool registry.

A future agent runtime must provide an equivalent adapter seam before migration acceptance.
