## Why this checkpoint matters

Live source inspection of `agent/system_prompt.py` proved that Hermes does not treat the system prompt as one undifferentiated stable block internally. `build_system_prompt_parts()` explicitly assembles three ordered cache tiers and then joins them into one provider-facing system message:

1. `stable` — cross-session-stable identity/guidance/runtime scaffold;
2. `context` — workspace/session-stable context and caller/project context files;
3. `volatile` — skills index, built-in memory, user profile, external memory-provider content, plugin tail, timestamp/session/model/provider/platform metadata.

The full joined string is cached per session and replayed verbatim across turns unless a rebuild boundary such as compression/restore occurs.

## Critical metric correction

The RYZ3N Cache Controller v0.1.2 field currently named `stable_prefix_fingerprint` / `stable_prefix_char_count` is generated from the leading non-user provider messages. In PRIME's current request shape, that leading prefix contains the full provider-facing system message, i.e. the joined Hermes `stable + context + volatile` tiers.

Therefore the prior E1.21 measurement:

- system-message / leading-prefix characters: ~32.8k;
- repeated share of message payload: ~98.8%;
- repeated share of request characters: ~98.1%;
- provider-reported cached input tokens on the measured Laguna call: 0;

remains valid as **repeated provider-request payload across the measured turns**, but it must NOT be interpreted as proof that ~98.8% of the request belongs specifically to Hermes' cross-session `stable` tier.

Correct terminology going forward:

- `leading_system_prefix_*` = the whole leading provider system-message prefix currently measured by the RYZ3N observer;
- `hermes_stable_tier_*` = only the `parts["stable"]` output from `build_system_prompt_parts()`;
- `hermes_context_tier_*` = only `parts["context"]`;
- `hermes_volatile_tier_*` = only `parts["volatile"]`.

Future telemetry should preserve this distinction so dashboard/cache decisions do not conflate request continuity with cross-session-stable semantics.

## Proven Hermes composition order

### Stable tier

Observed source contributions include, subject to runtime gates:

- SOUL.md identity or hardcoded default identity;
- Hermes help guidance;
- task-completion guidance;
- parallel-tool guidance;
- tool-aware behavioral guidance such as memory/session-search/skills/kanban guidance;
- steer-channel note;
- tool-use-enforcement guidance where applicable;
- model-specific operational guidance where applicable;
- execution-discipline guidance where applicable;
- model/provider-specific identity additions where applicable;
- environment hints;
- coding operating brief/static coding prefix;
- post-workspace/session-profile/platform guidance that remains session-stable.

Hermes stores this tier on `agent._cached_system_prompt_static`.

### Context tier

Observed source contributions include:

- coding workspace snapshot and trailing coding context where enabled;
- caller-supplied `system_message` when present;
- cwd/project context files from `build_context_files_prompt()`.

This tier may differ between sessions/workspaces even if it stays fixed during one session.

### Volatile tier

Observed source contributions include:

- runtime-mutable skills index;
- built-in MEMORY.md snapshot;
- USER.md profile snapshot;
- external memory provider system-prompt block;
- plugin sections after memory;
- date/timezone/session/model/provider/platform line.

Hermes intentionally renders volatile material last to preserve the longest possible reusable prefix on implicit longest-prefix cache backends.

## Existing Hermes cache architecture confirmed

Source inspection also confirmed Hermes already provides:

- per-session cached system-prompt persistence/reuse;
- `_cached_system_prompt_static`;
- `reconstruct_static_prefix()`;
- stable-prefix registration/boundary logic;
- prompt-cache scope resolution;
- `build_prompt_cache_plan()`;
- backend-specific cache marker support;
- comments/invariants explicitly protecting byte-stable prefixes.

RYZ3N must extend these supported seams rather than create a competing second prompt/cache architecture.

## E1.22 implementation constraint

Do not remove prompt content merely because it repeats. A remote stateless provider still requires all instructions/context that are semantically necessary unless the provider itself retains them through supported server-side context/KV caching.

The active efficiency intervention must therefore separate:

- always-on constitutional/runtime kernel;
- session/workspace context that can remain cached/stable;
- volatile material that should remain late in the prefix;
- doctrine/context that can be safely retrieved/injected only when relevant;
- genuine duplication/legacy material that can be removed without capability loss.

No active compiler mutation is accepted until tier sizes are measured separately and behavior parity is proven in shadow/before-after tests.
