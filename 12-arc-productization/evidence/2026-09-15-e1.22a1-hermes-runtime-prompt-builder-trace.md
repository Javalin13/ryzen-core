## Evidence

Live VPS source trace showed that Hermes already implements cache-aware system-prompt construction and replay. Relevant source surfaces include:

- `agent/system_prompt.py`
- `agent/prompt_builder.py`
- `agent/prompt_cache_boundary.py`
- `agent/prompt_cache_scope.py`
- `agent/prompt_caching.py`
- `agent/conversation_loop.py`
- `agent/chat_completion_helpers.py`

The live source explicitly shows:

- the system prompt is cached once per session (`agent._cached_system_prompt`);
- the static cacheable portion has a separate representation (`agent._cached_system_prompt_static`);
- continuing sessions restore the exact stored system prompt from the session database;
- the final request prepends the cached system prompt to provider messages;
- Hermes intentionally keeps dynamic per-turn material out of the stable system prefix because system-prompt mutation breaks provider prefix caching;
- failover redecoration can reconstruct the static prefix;
- `build_prompt_cache_plan(...)` already exists and is used by the live conversation loop;
- prompt-cache boundary logic exists as first-class Hermes runtime code.

## Architectural conclusion

Do not build a competing cache/context architecture beside Hermes and do not rewrite the agent loop.

The RYZ3N performance layer must extend the existing cache-aware prompt builder surgically:

1. preserve Hermes' byte-stable system-prefix contract;
2. classify the composition inputs that make up PRIME's ~32.8k stable system message;
3. reduce only material that can safely become conditional/retrievable;
4. preserve an always-on constitutional/governance kernel;
5. keep the resulting compiled prefix byte-stable for provider cache compatibility;
6. validate semantic parity before any live activation.

## Important correction

The stable PRIME prefix is runtime-generated, not a historical `messages.content` row. State DB inspection found only large tool/session payloads in the matching size range. The runtime prompt builder is therefore the correct intervention surface.
