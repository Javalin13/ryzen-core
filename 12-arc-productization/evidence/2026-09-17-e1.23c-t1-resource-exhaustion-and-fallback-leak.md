## Live test context

After Cognitive Connection v0.1.0 deployment, Doctor validation, PRIME-only restart, and T0 exact/direct GREEN, T1 was run through the real Founder → PRIME Telegram path.

The T1 answer itself was fast and semantically relevant, but the test exposed two real acceptance blockers and one test-design issue.

## Proven provider-side failure

PRIME logs at approximately 14:58:26 CEST show the primary Poolside Laguna route failed on the first visible API attempt with:

`ResourceExhausted: Worker local total request limit reached (119/32)`

The failure occurred before delivery. The log also shows `attempt 1/1`, so this specific T1 turn did not first enter a long recursive retry chain before the primary route failed.

This proves a current provider-capacity/resource boundary. It does not by itself prove the exact semantics of the provider's `119/32` counter, and that should not be guessed.

## Fallback behavior

After the primary failure, PRIME fell back to the local Qwen route and returned quickly enough to preserve interaction continuity.

The Owner-facing Telegram notice exposed implementation/provider details in the form of a model/provider fallback message. That violates the current output-discipline rule for Founder-facing operation.

Internally, Hermes generated the notice in `agent/chat_completion_helpers.py` and buffered it through the status path. The current user-facing wording also conflates the local Qwen model with its serving/runtime provider label (`local-ollama`).

The public UX should not expose model/provider/runtime internals. If degradation must be surfaced, it should use an implementation-neutral continuity/degraded-mode message.

## Test-design correction

The T1 prompt required `one short sentence`, so the shortness of the answer cannot be used as evidence that PRIME naturally under-answered. Future T1 conversational acceptance must ask for a normal appropriately complete response rather than artificially constraining length.
