# E1.24 — Cognitive Connection v0.3 Middleware Registration Probe RED

Date: **2026-09-17**  
Master: **M3/16 — Cargo ARC GREEN**  
Line: **E1.24 context/capacity pressure reduction**

## Purpose

Prove whether the deployed `ryz3n-cognitive-connection` v0.3.0 request-local `llm_request` middleware is actually registered and reachable through Hermes' real plugin machinery.

## Context

v0.3.0 was introduced to remove provider tool schemas from request-local R0/R1 turns without mutating `agent.tools` or Hermes core.

Expected runtime behavior:

```text
R0/R1 classification
→ store turn-local lane state
→ llm_request middleware
→ strip tools/tool_choice/etc from provider request
→ leave canonical agent.tools untouched
```

Live telemetry after deployment did **not** show payload narrowing:

- post-v0.3 request still matched prior request size/fingerprint;
- `middleware_trace_count = 0`;
- provider input remained high;
- therefore the live request was not rewritten.

## Synthetic probe

A bounded, no-provider-call probe was executed with the real Hermes Python environment and plugin machinery.

The probe:

1. invoked `pre_llm_call` using a synthetic session/turn and explicit no-tool message;
2. created a synthetic provider request containing a tool schema and `tool_choice`;
3. applied `apply_llm_request_middleware(...)` using the same synthetic session/turn;
4. inspected middleware registration and resulting payload.

Observed result:

```text
has_llm_request_middleware = False
changed = False
trace_count = 0
tools_before = True
tools_after = True
tool_choice_after = True
```

## Conclusion

**RED:** the standalone Cognitive Connection plugin is not registering/reaching `llm_request` middleware in the synthetic Hermes process, even though its hooks are available through Plugin Doctor/runtime behavior.

This disproves the earlier assumption that `ctx.register_middleware("llm_request", ...)` was already sufficient in the current standalone deployment context.

## Eliminated hypotheses

Evidence already eliminated:

- different hook vs middleware delivery manager: both route through `_delivery_manager()`;
- separate `provides_middleware` manifest declaration: none is required by the registration API contract;
- obvious turn-id mismatch: `turn_id` is propagated from `build_turn_context()` through the request path and into middleware context;
- request-rewrite contract itself: Hermes middleware explicitly accepts `{"request": {...}}` replacements.

## Current narrow blocker

Determine why the standalone plugin's `register(ctx)` successfully establishes hooks but does not result in visible `llm_request` middleware registration in the real plugin manager used by the probe/gateway.

No model change, prompt trimming, Telegram changes or broad Hermes redesign are authorized by this evidence.

## Portability implication

This is exactly why RYZ3N must document the distinction between:

- RYZ3N-owned semantic contracts; and
- Hermes-specific adapter/registration mechanics.

A future agent-runtime migration should reuse the semantic contract and replace only the runtime mapping.

## Acceptance to close this RED

GREEN requires:

```text
has_llm_request_middleware = True
changed = True
trace_count >= 1
tools_after = False
tool_choice_after = False
```

followed by one live PRIME R1 request whose effective provider payload is measurably narrowed.
