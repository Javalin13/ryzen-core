# E1.22M — Shared system-prompt adoption boundary GREEN

Date: 2026-09-15

## Result
Source tracing proved that fresh and restored PRIME sessions converge through `agent/conversation_loop.py::_restore_or_build_system_prompt(...)`.

- Fresh session: builds through `agent._build_system_prompt(...)` and stores the result on `agent._cached_system_prompt`.
- Continuing session: restores/adopts `stored_prompt` directly into `agent._cached_system_prompt`.
- `agent/turn_context.py` then consumes `agent._cached_system_prompt` as the active system prompt for the turn.

Therefore `_restore_or_build_system_prompt(...)` is the common prompt-adoption boundary for both fresh and long-lived/restored sessions. This explains why build-only telemetry in v0.1.5 can be absent on a restored Telegram session even though the provider-facing system prompt is present.

## Engineering consequence
Future provider-independent tier instrumentation must cover this shared adoption boundary, not only `build_system_prompt()`. Any restored prompt must be classified/reconstructed safely without rewriting stored prompt bytes.

## Constraint
No prompt-content mutation, provider routing change, Cargo change, or Telegram-network change is justified by this evidence alone.
