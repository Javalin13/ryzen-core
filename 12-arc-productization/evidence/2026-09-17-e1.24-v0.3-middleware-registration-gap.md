# E1.24 — Cognitive Connection v0.3 Middleware Registration Gap

Date: 2026-09-17
Status: RED / unresolved
Scope: request-local tool-schema suppression for R0/R1

## Objective

Prove that Cognitive Connection v0.3 removes provider tool schemas on direct/no-tool turns without mutating `agent.tools`.

## Expected path

```text
pre_llm_call
→ classify R0/R1
→ store per-turn lane state
→ Hermes build provider kwargs
→ llm_request middleware
→ strip tools/tool_choice/etc from this request only
→ pre_api_request observes changed request
→ provider receives smaller payload
```

## Live behavioral result

The post-v0.3 T3 no-tool weather test remained behaviorally bounded and did not invoke tools. However the primary Laguna request again failed provider-side and fell back to local Qwen.

Behavioral boundedness therefore remains GREEN from v0.2 logic, but E1.24 capacity/tool-payload reduction is NOT proven.

## Live telemetry result

For the post-v0.3 request around 2026-09-17 16:14 CEST:

- `middleware_trace_count = 0`
- `request_char_count = 33112` for Laguna
- request fingerprint `95541ce4a46cbd409fc2df03f3db1a61dbbc84283ff369edff7699406b8e79e0`
- telemetry still reports canonical `tool_count = 21`

The same request size/fingerprint appeared before v0.3 for the equivalent fresh-session T3 test. Therefore no effective request mutation is evidenced.

Important nuance: telemetry `tool_count` is supplied from canonical `agent.tools` and by itself does not prove whether middleware stripped request-local tool schemas. The unchanged request fingerprint/size plus zero middleware trace is stronger evidence that the middleware did not alter the request.

## Source-contract facts proven

Hermes source inspection showed:

1. `build_api_kwargs(agent, ..., tools_for_api=...)` supports a request-local tool list.
2. `apply_llm_request_middleware(api_kwargs, ...)` runs after provider kwargs are built and before `pre_api_request`.
3. request middleware may return `{"request": {...}}` to replace effective provider kwargs.
4. `PluginContext.register_middleware("llm_request", callback)` stores middleware callbacks in the plugin manager.
5. no separate `provides_middleware` manifest declaration was found/required by the registration API.
6. hooks and middleware dispatch both resolve via the same `_delivery_manager()` / active plugin manager.
7. static turn-id inspection indicates `pre_llm_call` and the API-request path use the same conversation-loop `turn_id` lineage.

These findings eliminate several earlier hypotheses: wrong hook type, mandatory manifest middleware declaration, different hook/middleware managers, and obvious turn-id lineage mismatch.

## Synthetic probe

A standalone Hermes-venv Python probe was run with `HERMES_HOME=/home/prime/.hermes`.

Probe sequence:

- invoke `pre_llm_call` with explicit no-tool text;
- create request containing `tools` and `tool_choice`;
- call `apply_llm_request_middleware(...)`;
- inspect middleware availability and effective payload.

Observed:

```text
has_llm_request_middleware = False
changed = False
trace_count = 0
tools_before = True
tools_after = True
tool_choice_after = True
```

Interpretation:

The standalone process did not expose the expected registered `llm_request` middleware. This is a high-value clue about plugin discovery/loading state. It is NOT sufficient on its own to claim the live gateway has no middleware registration, because the live gateway process and standalone probe may have different discovery state/lifecycle.

## Current narrowed hypotheses

Only high-value remaining hypotheses should be investigated:

A. user plugin discovery/loading in the standalone/live middleware surface differs from hook delivery lifecycle;
B. the Cognitive Connection plugin is loaded for hooks but its middleware registration is not retained/exposed in the active gateway manager;
C. a lifecycle reload/unload path removes middleware while hook callbacks remain;
D. the live runtime imports/uses a plugin-manager instance or discovery state not captured by the static source assumptions despite shared helper functions.

Do not reopen model selection, Telegram logic, prompt trimming, or cache architecture to solve this issue.

## Acceptance

E1.24 request-local tool suppression becomes GREEN only when evidence shows on an R0/R1 turn:

- middleware is present/invoked;
- `middleware_trace_count >= 1` or equivalent direct evidence;
- provider request no longer includes tool schemas;
- canonical `agent.tools` remains available after the turn;
- R2+ tool-capable turn still receives tools;
- input/request payload reduction is measured;
- no behavioral regression.

## Rollback boundary

Cognitive Connection v0.3 is additive and isolated to the RYZ3N plugin. No Hermes core reset/rewrite is authorized. If request middleware remains unreliable, preserve v0.2 bounded cognition behavior and design the smallest runtime-adapter seam rather than coupling RYZ3N deeper into Hermes core.
