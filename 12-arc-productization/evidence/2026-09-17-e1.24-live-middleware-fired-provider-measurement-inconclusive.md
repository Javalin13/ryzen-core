## Live evidence

The post-enable live T3 turn produced a PRIME response that was behaviorally bounded and no-tool. Telemetry for the live provider path then showed:

- `middleware_trace_count = 1` on the Laguna request;
- `middleware_trace_count = 1` on the local fallback request;
- live middleware delivery therefore fired in production;
- prior pre-enable equivalent turns had `middleware_trace_count = 0`.

This closes the question of whether the enabled Cognitive Connection middleware is actually reaching the live provider request path.

## Why E1.24 is not fully GREEN yet

The existing capacity telemetry does **not** make a clean before/after tool-payload comparison possible:

1. `tool_count = 21` is not authoritative evidence that tools remained in the effective rewritten request; this field reflects the canonical runtime tool registry rather than the post-middleware request-local payload.
2. `request_char_count` and `approx_input_tokens` are dominated by message/system content and differ across turns because conversation history and injected turn policy changed.
3. The live Laguna request failed with provider/resource error before returning authoritative provider `input_tokens`, so no provider-token comparison exists for that primary call.
4. The local fallback provider's `input_tokens = 2050` is not directly comparable to Laguna's earlier ~20k input-token accounting because the provider/tokenizer/runtime path differs.

Observed live request after enable:

```text
middleware_trace_count = 1
model = poolside/laguna-xs-2.1
request_char_count = 33908
approx_input_tokens = 8477
message_payload_char_count = 33775
```

Observed earlier pre-enable no-tool baseline included:

```text
middleware_trace_count = 0

approx_input_tokens = 8278
provider input_tokens ≈ 20k on successful Laguna calls
```

The larger post-enable request chars do not imply middleware regression; the compared turns do not have equivalent history/message content. Therefore no material reduction claim is made from those fields.

## Smallest next step

Do **not** continue source archaeology or provider/model hunting.

Add one measurement-only field at the post-middleware request boundary (or derive it inside the existing cache-controller telemetry hook) that records the effective request-local tool payload after middleware, without logging raw tool schemas. Minimum useful fields:

- `effective_tool_payload_present: bool`
- `effective_tool_count: int | null`
- optionally `effective_tool_payload_char_count: int | null`

This must be telemetry-only, content-free, and must not mutate cognition or provider behavior.

Then rerun one equivalent fresh-session R1 no-tool turn and compare to a fresh-session R2/tool-capable control.

## Portability lesson

A portable RYZ3N runtime adapter must expose post-policy **effective capability payload** telemetry. Canonical runtime capability count and model-facing request capability count are different concepts and must not be conflated.
