## Founder decision

For the personal/owner ARC product/runtime pattern, one ARC instance serves one Owner/Person as a coherent intelligence layer across that person's relevant life and work context.

Inside that ARC instance, work is resolved through the following runtime context chain:

```text
ARC instance
  ↓
Domain / Project
  ↓
Intent
  ↓
Activity
  ↓
Corresponding Brain
  ↓
Agents
  ↓
Execution
```

This is an **instance-level runtime refinement** beneath the canonical ARC layer. It does not rewrite the canonical ontology:

`Creator → RYZ3N → ARCs → Brains → Agents → Execution`

The canonical ARC remains the framing authority. The runtime refinement makes that framing operational for an Owner/Person by resolving context before a Brain is selected or created.

## 1. ARC instance

The ARC instance is the coherent intelligence environment serving one Owner/Person.

It must preserve:
- owner identity and delegated authority;
- memory and privacy boundaries;
- durable context across multiple domains/projects;
- one coherent relationship with the Owner;
- constitutional limits and upward evidence flow.

The ARC must not split into a separate ARC merely because the Owner has multiple domains or activities.

## 2. Domain / Project

A Domain/Project identifies the area of reality in which the Owner wants to think, decide, build or act.

Examples:
- business development;
- restaurant / hospitality;
- real estate;
- writing;
- styling;
- family;
- personal finance;
- a future business idea;
- a project that has not yet started.

A Domain/Project may exist before execution begins.

Required state classification:
- `idea`
- `planned`
- `preparing`
- `active`
- `validated`
- `paused`
- `closed`

These runtime labels must be mapped truthfully to the Interpretation Protocol. A planned project is not reality merely because it has a folder or description.

## 3. Intent

Intent records what the Owner wants to undertake, achieve, change, decide or make happen inside a Domain/Project.

Intent is upstream of Activity.

Examples:
- increase restaurant orders;
- open a second location;
- improve lead conversion;
- write and publish a book;
- professionalize a styling service;
- improve real-estate portfolio performance.

The ARC may clarify, structure and preserve Owner intent. It may not fabricate it.

## 4. Activity

Activity is the concrete class of work required to serve an Intent.

Examples:
- answer customer questions;
- follow orders;
- qualify leads;
- prepare proposals;
- track tenants and maintenance;
- draft chapters;
- schedule social posts;
- reconcile bookkeeping documents.

Activities are functional work units. They are not automatically Brains.

## 5. Corresponding Brain

A Brain is the specialized reasoning unit that corresponds to a stable class of Activity when such specialization is materially justified.

The ARC first resolves:

`Domain/Project → Intent → Activity`

Then it:
- routes the Activity to an existing corresponding Brain; or
- if no suitable Brain exists and the reasoning pattern is stable/material, self-provisions a new Brain under `BRAINS/<SPECIALIZATION>/`.

A one-off Activity must not force a new Brain.

## 6. Agents and Execution

Brains reason. Agents execute within the Brain's frame. Execution touches reality.

Required chain:

`Owner intent → Domain/Project context → Activity → Brain reasoning → authorized Agent → Execution`

Upward evidence returns:

`Execution → Agent → Brain → Activity result → Intent progress → Domain/Project state → ARC → PRIME/RYZ3N-readable convergence → Owner/Founder`

## 7. Projects that do not yet exist in reality

The ARC may hold future projects before implementation.

Example:

```text
ARC
→ Domain/Project: second restaurant location
→ status: planned
→ Intent: open a profitable second location
→ Activities: location research, budget, permit research, supplier planning
→ corresponding Brains as justified
→ Agents/Execution only when authorized actions actually occur
```

The ARC must never report the project as active/operational if evidence only supports planned/preparing.

## 8. Brain emergence rule

The Brain map is emergent from real Owner needs.

Correct sequence:

`Owner → Domain/Project → Intent → Activity → reasoning need observed → existing Brain or candidate Brain → Brain contract → Agent → Execution → evidence`

Not:

`prebuilt Brain catalogue → search for work to justify it`

## 9. PRIME / BRAIN STEWARD boundary

PRIME/BRAIN STEWARD may supervise:
- Domain/Project identifiers and non-private status metadata;
- Brain identity/status and source pointers;
- Activity-to-Brain routing contract shape;
- Agent authority/evidence boundaries;
- constitutional drift.

It must not:
- own the Owner's private context;
- invent Owner intent;
- decide the Owner's Domain/Project priorities unless explicitly delegated;
- create speculative Brain taxonomies;
- become an ontology tier between ARC and Brain.

## 10. Three-pass constitutional verification

For every material implementation of this hierarchy:

### PASS 1 — CANON / REALITY
Read the current canonical sources and verify the real repository/runtime state. Do not infer implementation from documentation.

### PASS 2 — IMPLEMENTATION ALIGNMENT
Verify that the runtime preserves canonical authority and the Founder-approved instance refinement:

`ARC instance → Domain/Project → Intent → Activity → Corresponding Brain → Agents → Execution`

### PASS 3 — EVIDENCE / FINAL STATE
Prove the final state with current repository/runtime evidence. Distinguish implemented, active execution, approved architecture and planned.

If any pass fails, surface drift, correct, and rerun all three from PASS 1.

## Founder principle

> One Owner is served coherently by one personal ARC instance. The ARC understands the Owner's Domains and Projects, preserves the Owner's Intent, resolves that Intent into Activities, and brings in or creates the corresponding Brain only when reality requires specialized reasoning. Agents execute; evidence returns upward.
